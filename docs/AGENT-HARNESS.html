The clinical review agent: how the agent part works

This page covers the agent part: the loop, the tools, where each piece runs, and where the output goes. It also replays two real runs step by step, and explains the Databricks AI services we would use on a sponsor's platform. For the business story, see OVERVIEW.html.

Straight answers

Is it the Claude Agent SDK?
No. It uses the plain Anthropic Python SDK (pip install anthropic), calling client.messages.create(...) with tool definitions. Our harness wraps it in an adapter called AnthropicClient. The Claude Agent SDK was considered and dropped (decision D6): it is built for coding agents, with bash and file tools we don't want next to trial data.
Is the loop our own?
Yes. The loop is agent_harness.loop.run() from our shared harness library, the same one the FNOL agent uses. It calls Claude, runs the tools Claude asks for, sends the results back, and repeats until Claude finishes or a limit is hit. This repo only supplies the prompt, the tools and the limits (src/clinical_review/run.py).
Where are the tools? Is it MCP?
Not MCP. The tools are plain Python methods on a class called PatientTools (src/clinical_review/tools.py). They are registered with the harness as in-process tools (LocalTool), so they run inside the same Python process as the loop, with no server and no network hop. MCP would add a server and authentication for no gain while only one agent uses these tools. That changes on Databricks: see MCP on Databricks.
Where does the data come from?
From one stamped snapshot of the curated trial tables, saved as Parquet files under data/curated/snap-…/ and read by ParquetTrialData. The treatment arm and dose are removed before the agent can see anything. On Databricks the same reads would point at Unity Catalog tables.
Where does the agent's output sit?
In three places:
1. Draft queries: runs/drafts.jsonl, one line per draft with status pending_review. This is the agent's only write.
2. Run record: runs/<run_id>/record.json holds the snapshot, versions, tool calls, tokens, cost and how the run ended.
3. Trace: runs/<run_id>/spans.json has an OpenTelemetry span for every model and tool call.
Where does it run, and who starts it?
Today it runs as a Python process on the Mac, either python -m clinical_review.run 01-705-1186 for one patient or the batch runner for 40 patients. One run reviews one patient. On Databricks, the target is a Databricks Job that runs the same package, 4 patients at a time. Claude Opus 5.5 is called through the Anthropic API today, and through Databricks Model Serving on the target.

The loop, in plain words

One round is a "step". The harness sends Claude the system prompt, the task and everything so far, plus the definitions of the 11 tools. Claude answers in one of two ways:

• stop_reason = "tool_use": Claude asks for one or more tools, for example three lab_trend calls at once. The harness checks them against policy, runs them in parallel, wraps each result as a tool_result, appends them to the conversation, and goes round again.

• stop_reason = "end_turn": Claude writes its final summary. The run ends as goal_reached.

Limits end a run early and are recorded: 12 steps, 180 seconds, $0.50, 8 tool calls per step, 24 per run, or the same tool called twice in a row with the same arguments. The run then ends as "could not complete", and anything it found so far is kept.

Who does what. The harness library owns the loop, retries, budgets, tracing and cost. This agent's code owns the prompt, the tools and the draft store. Claude only decides which tool to call next and what to write.

The real run: patient 01-705-1186 took 5 steps, made 16 tool calls, took 41 seconds and cost $0.19. Replay it in the simulation.

The tools

All 11 tools are methods of PatientTools in src/clinical_review/tools.py, run in-process. No tool takes a patient ID: the run fixes the patient when PatientTools is created, so the agent cannot read anyone else, whatever a prompt says. Code does the arithmetic (multiples of the normal limit, dates), and every fact carries a src_ref pointing at the exact record.

Guards on every result (tools.py: _guard):
• The blinding check raises an error if a treatment-arm column appears.
• Site-typed text arrives as {"untrusted_text": …}.
• Results over 16,000 characters are cut with a note.
• A failure goes back to Claude as an error, never as empty data.

    Databricks AI, explained for this agent

    On a sponsor's Azure Databricks, these are the pieces we would use, and what each does for us. What we would use is marked Use; what we would not use is marked Skip. Databricks renames and extends these services often, so check the names in the workspace before quoting them.

    Model ServingHosts a model behind a REST endpoint in the workspace. There are three kinds of endpoint: Foundation Model APIs (models Databricks hosts, including Claude, paid per token or as provisioned throughput), external models (a proxy to Anthropic's API using a key stored in Databricks secrets), and custom models.
    Use: a Claude endpoint becomes our model route. We add a second adapter for the same model port, so only the address and credential change. The loop and tools stay as they are.
    AI GatewaySettings on a serving endpoint, not a separate product. They give usage tracking (who used how many tokens, in system tables), inference tables (every request and response saved to a Delta table), rate limits per user or endpoint, guardrails (PII and safety filters), and fallbacks between models.
    Use: inference tables give the auditor every prompt and answer next to the trial data; rate limits back our $20-a-day ceiling. Treat its PII filter as a second line after our own minimising.
    How the code calls itServing endpoints take an OpenAI-style chat API, and the Databricks SDK and MLflow deployments client can call them too. Authentication uses a service principal (a non-human Databricks identity) with an OAuth token, so there is no Anthropic key in the app.
    Watch: Claude features such as extended thinking blocks or prompt caching may lag behind Anthropic's own API. Our harness passes thinking blocks back unchanged (F-2), so test that first.
    MLflow TracingRecords each agent run as a trace: every model call, tool call, input, output, tokens and time, viewable in the MLflow experiment UI. It accepts OpenTelemetry.
    Use: our harness already emits OpenTelemetry spans (today saved as spans.json). On Databricks we point the exporter at MLflow, with no code change in the agent.
    Unity CatalogThe governance layer: tables, volumes, functions and models, with permissions and lineage.
    Use: curated snapshot tables (read-only grant for the agent's principal), the drafts table (insert only), and lineage from OpenClinica to snapshot to draft.
    MCP on DatabricksDatabricks offers managed MCP servers that expose Unity Catalog functions, Vector Search and Genie spaces as tools, and you can host your own MCP server as a Databricks App.
    Not now: one agent uses these tools, so in-process is simpler. Move them to MCP when several agents share them. The patient binding would then move into the server, as a token scoped to one patient.
    Mosaic AI Agent Framework / Agent BricksDatabricks' own way to build and deploy agents: a standard agent interface, one-command deploy to a serving endpoint, a review app, and Agent Evaluation with LLM judges.
    Skip, by choice: we keep our own loop on the shared harness so the same code, gates and tests serve every agent and every cloud. Their evaluation judges could be tried as an extra judge.
    Databricks Jobs and AppsJobs run code on a schedule or trigger, on serverless compute. Apps host small web apps inside the workspace, signed in with workspace identity.
    Use: a Job runs the nightly review batch, 4 patients at a time. An App is the data manager's approval screen.
