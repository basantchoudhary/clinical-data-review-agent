Clinical Data Review Agent

An AI agent that reviews one clinical-trial patient's record across forms and visits, finds the inconsistencies that simple field checks cannot judge, and drafts precise queries for a data manager to approve. It never changes trial data and never sends anything itself.

1. The problem it solves

A clinical trial's data has to be clean before the database can be locked and analysed. Data is entered by hospital staff (sites) into an EDC system, one form at a time. Two kinds of checking clean it:

Edit checksData review
Done byThe EDC, automaticallyData managers and a medical monitor, by hand
Looks atOne field or one formThe whole patient, across forms and visits
Catches"ALT is above range""ALT is three times normal and bilirubin is rising, yet no liver event is recorded"
CostNearly freeSlow, repetitive, expensive expert time

Data review is where the work and the risk sit. A reviewer opens a patient, reads across six or seven tables, and decides what is worth asking the site. Most patients are fine; finding the few that are not, and asking the right question, is the skill. Under time pressure, reviews get shallower, cross-form problems are missed, and vague queries go back and forth with sites, which delays database lock.

2. Business benefit

Every patient gets a full first passThe same depth for patient 1 and patient 300, at any hour. Reviewers start from a prepared case instead of a blank screen.
Expert time moves to judgementReading, cross-referencing and drafting are done; the data manager decides, edits and approves. Fewer hours per patient on the mechanical part.
Better queries, fewer round tripsEach draft cites exact values, dates and records, asks rather than tells, and targets the right form. A specific query is answered once.
Problems found earlierCross-form issues such as a missing adverse event, a wrong onset date or an eligibility question surface during the study, not at lock.
Audit-ready by designEvery run records the data snapshot it read, the model and prompt versions, each tool call, cost, and who approved what. That is the trail an inspector asks for.
Cheap to run, measuredThe first real review cost $0.19 and took 41 seconds. Cost per patient is a release gate, not a guess.
What it is not. It does not replace data managers or investigators. It does not make clinical judgements (it asks, the investigator decides). It never sends a query or changes data: a person approves every query, and a separate program, with no AI in it, posts approved ones. Its value claims are measured before they are made (section 8).

4. Why this is agentic, and why most of it is not

An agent is worth its cost and risk only when all four of these hold. Data review passes all four:

TestClinical data review
Is the path unknown in advance?What to look at next depends on what was just found: a high lab leads to adverse events, then to an onset date, then to the protocol's entry criteria, then to disposition. Each patient takes a different path.yes
Does it need several sources?Five or more tables plus the protocolyes
Is judgement the hard part?Deciding what is worth asking, and when a pattern does not apply (for example a high ALP explained by bone disease, not liver)yes
Can mistakes be caught?A data manager approves every query before it reaches a siteyes

The architect's point: most of the system is deliberately not an agent. Rules are cheaper, exact and easier to defend to an auditor, so everything a rule can do stays a rule:

PieceBuilt asWhy
Loading data, SDTM-aligned layersPipelineReproducible and auditable
Edit checks (out of range, impossible dates)RulesExact and explainable
Which patients to review firstRulesA score from the rule hits
Reviewing one patient across forms; drafting queriesAgentPasses all four tests
Approving and sendingPerson plus a plain programAccountability stays human; the only writer has no AI in it

5. Architecture

How one patient flows through it

  1. The pipeline exports from OpenClinica, builds the curated layers, runs the edit checks and ranks patients. Every row carries a snapshot ID and a link back to its OpenClinica field.
  2. A worker picks the next patient. The harness starts a run bound to that patient and that snapshot.
  3. Claude reads a one-page summary, then drills in with the tools. Code does the arithmetic (for example "3.25 × the upper limit"); the model decides what it means.
  4. For each real inconsistency it saves a draft query, citing the records it relied on. The tool refuses evidence that does not exist in that patient's snapshot.
  5. A data manager approves, edits or rejects each draft. Edits and rejection reasons are kept: they measure the agent's quality.
  6. The writer re-reads the field in OpenClinica. If it changed since the snapshot, the draft goes back for re-review; otherwise it is posted as a discrepancy note.

Built on the AgentHarnessSuite

Ports and adapters, like the reference agents: every outside system sits behind an interface, and configuration chooses the implementation. Trial data has a local adapter (development) and a Databricks adapter; the model has an Anthropic adapter whose address switches it to Databricks Model Serving with no code change. The suite's catalogs check the design: AHC (what a production harness must contain: all 16 layers decided), AAC (what must be true: obligations such as least privilege, no action on a stale read, gated actions), AgentTwin (a simulated trial with planted problems) and the Eval Harness (checks on every output).

7. How it is proven

Nobody should trust it because a demo looked good. Before release, a version must pass gates set in advance:

≥ 80%of planted problems found, in a simulated trial with known defects and clean patients
≥ 70%of drafts judged worth sending by a human labeller, with Claude as a judge only once it agrees with her
0blinding or privacy failures; every evidence reference exists
≤ $0.30per patient, and no worse than the previous version

At a real sponsor it would then run in shadow mode, drafting beside human reviewers without sending anything, until agreement is measured. It never earns sending without approval.

8. First result

The first real run, on pilot patient 01-705-1186 (CDISC pilot study, an 84-year-old patient whose liver tests rose after starting): 5 steps, 16 tool calls, 41 seconds, $0.19, all served by Claude Opus 5.5. It drafted five queries, including the four a human reviewer had identified in advance, and one more:

Adverse events, onset date. Bilirubin was already 5.5 × the upper limit on 23 Jan; the event starts 26 Jan. Please check the onset date.
Adverse events, possible missing event. ALT and AST reached 3–4 × the upper limit with bilirubin above 2 ×; no event covers the transaminase rise. Investigator to assess.
Eligibility. Screening ALT, AST and bilirubin were above range; exclusion criterion EXCL27. Please confirm eligibility or a documented exception.
Laboratory, visit date. Labs labelled Week 4 are dated 29 Jan; the Week 4 visit is recorded on 7 Feb.
Adverse events and disposition. "Action taken" is blank; withdrawn by "physician decision" for hyperbilirubinemia. Should the reason be adverse event?

It also noted from the medical history that the patient has Paget's disease of bone, which explains the high ALP, and correctly did not raise a query about it. A single patient is a demonstration, not proof: the measured results come from Phase 2 of the plan.
